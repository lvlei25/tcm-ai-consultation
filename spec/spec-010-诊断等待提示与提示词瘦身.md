# spec-010：诊断等待提示与提示词瘦身

对应基线：spec-001、spec-002、spec-003、spec-009

## 变更原因

用户反馈浏览器端「卡在生成诊断结果」。实测定位（2026-10-17）：

| 阶段 | 耗时 |
|---|---|
| 知识库加载 | 0.6s |
| 检索语句生成 | ~40s |
| 混合检索 | 0.6s |
| 诊断首个输出字 | 再等 ~134s（独立复测 124.5s） |
| 后续 3139 字流式输出 | ~40s |

- 已排除「思考内容被丢弃」：流中无 `reasoning_content`
- 已排除代码阻塞：`stream_diagnosis` 生成器正常，短请求 1.7s 出正文
- 根因：`qwen3.8-27b` 对诊断长提示词（约 3000+ 字）服务端首 token 延迟约 2 分钟，
  期间界面只有 spinner 文案，被误判为卡死

## 变更内容（方案 A + B）

| 文件 | 变更 |
|------|------|
| app.py（A） | 步骤 3 在流式输出前显示等待提示（说明通常需 2~3 分钟）；首包到达后由生成器内清除提示，避免与正文混排；异常时同样清除 |
| config.py（B） | 新增 `EVIDENCE_SNIPPET_LEN = 300`：每条医案证据进入提示词的最大字符数 |
| pipeline/diagnoser.py（B） | `format_evidences` 对超长证据文本截断到 `EVIDENCE_SNIPPET_LEN` 并标注「（原文过长已截断）」，出处行不截断 |

## 验证

- A：浏览器步骤 3 立即出现等待提示，首包到达后提示消失，正文流式渲染
- B：实测截断后的诊断首包延迟，与基线 124.5s 对比，结论回写「验证结果」
- `python -m pytest tests/ -q` 全量通过，新增截断用例
- 诊断输出仍含六小节（spec-009 解析不回归）

## 注意事项

- 不引入 fallback：截断是明确的提示词策略并标注，不静默丢内容
- 不改变检索条数 `TOP_K=6` 与融合逻辑（spec-003/007 不回归）
- 模型仍为 `qwen3.8-27b`（spec-002 不变更）

## 验证结果（2026-10-17 执行）

- B 实测（同形态 6 条证据）：提示词 2581 字（截断 300/条），
  诊断首包 **124.5s → 35.9s**（-71%），总耗时 50.7s，输出 906 字
- 集成用例 `pytest -m integration`：3 passed（326.7s，含 3 次真实生成），
  截断后诊断仍含六小节，spec-009 解析不回归
- `python -m pytest tests/ -q` → 45 passed, 3 deselected（新增用例 48）
- A 界面：步骤 3 发起后立即显示等待提示（含「通常需 2~3 分钟」说明），
  首包到达后提示清除并流式渲染正文，异常时提示一并清除
